The Dumb Loop

The scaffold system restated as one coherent design. settled marks what you've already explicitly agreed — restated for coherence, not re-approval. needs yes marks everything else; per our standing rule, none of it is agreed until you say so.

The vision in five sentences

You confirm requirements in conversation; a blind planner turns them into a contract you approve — the tasks, how each is verified, what you'll be shown working, and the severity bar for review. A dumb script loop with no model in it lets worker agents pull tasks; the loop verifies their work itself and never trusts a self-report. Workers are interchangeable minds — claude, codex, whatever comes next — resolved through your roster; the loop doesn't know or care which vendor is behind an adapter. The run ends when the machinery proves done and presents you one handoff page; your "looks good" is the finish line, and it graduates the demonstrations into the blessed regression base the next flight checks against. Between approving the plan and reading that page, the run needs nothing from you except async answers to escalations.

YOU: intake→ YOU: approve plan→ loop: pull → dispatch → verify → flip→ escalations → your inbox (run continues)→ done-pending-bless→ handoff page→ YOU: stamp

settledPrinciples you've already agreed

  • One store, not two. The ledger is the task system: one current-state file plus an append-only journal of transitions. The journal is the old ledger's audit trail (every flip, its evidence, the commit it passed at) and nothing more — so nothing is lost in the merge, and there is no second system to drift. A task carries: its role profile, its check command, dependencies, typed attempt counts (work / infra / diagnostic — infra failures never burn budget), evidence with the commit it passed at, and separate completion and verdict fields (a review task passes on a complete review; its findings route to successor tasks — a truthful reviewer can always finish).
  • Pull, not push. An agent asks the loop for eligible work matching its profile — it never browses or chooses. One cycle: lease a task → do the work → land a candidate commit → the framework verifies that commit → the framework flips the state. A worker keeps cycling while it succeeds; a failure or a low context ends its slice. Claims are leases; an expired lease re-queues the task, so a dead agent's work recovers itself. Phases demote to affinity hints. The run is sequential in v1 — one worker at a time. (Even a "read-only" reviewer beside a writer would watch the worktree change under it; parallelism returns when readers can be given stable snapshots of the product, deliberately cut from v1.)
  • Three anchors, chosen deliberately at plan time. Expected values come from reality (a reference binary, the far side of a wire), from spec (transcribed tables), or from your judgment — blessed goldens. The third is the correct anchor for surfaces where "right" means "looks right to you".
  • Goldens vs. anchors. Goldens are regression snapshots: worker-creatable, regenerable on demand, blessed by you — ordinary engineering, zero ceremony. Anchors are artifacts the goal function depends on: made outside the worker loop, never worker-regenerated. Deliberately conflating them — "the goal function is: produce candidate goldens I stamp" — is legitimate for judgment-anchored work.
  • The goal function layers. A mechanical core (checks against anchors and the previously blessed set) runs red-first from a walking skeleton; the handoff-scrutiny chain is the terminal task sequence. Internal done is three file checks: core green, every planned demonstration has a fresh candidate — "fresh" meaning replayed or regenerated against the commit actually presented, never a stale first-pass capture — and production scrutiny complete. Then the run stops at done-pending-bless and presents.
  • Done is the machine's claim; accepted is yours. Your stamp on the handoff page is acceptance — it records a judgment you just exercised watching the demonstrations (nothing like the old promote-bytes act). A refused stamp is classified, not punished: a visible defect already inside the plan's own words gets one bounded remediation round — fix, re-verify, re-capture the demonstration, one return of the ask; an expectation the plan never contained routes to revision or fresh intake. Neither is ever a retry loop chasing your satisfaction.
  • Review never terminates on satisfaction. Loops are bounded by a severity bar fixed at plan time; the independent reviewer gates delivery, and verification authority remains yours personally.
  • Escalations are recorded, never waited on — fixed shape (blocked on X; I would do Y; here is what that would affect; veto or confirm). v1 makes no delivery promise: questions are surfaced first whenever you return or any agent attaches, the agent you answer turns your reply into the recorded ruling and unparks the work, and the run continues on independent tasks meanwhile.
  • Attending contexts are disposable. All state lives on disk; any fresh agent answers "what's the status?" by reading the store — and opens the handoff page for you when the answer is "done".

needs yesThe framework: shipped code, five pieces

The measured cost of not shipping it: yesterday's flight wrote 6,327 lines of throwaway Python to run itself, spent ~60–70% of its effort on its own machinery, and needed ~60 relaunches because nothing owned the driver's lifetime. Every piece below exists to make that impossible to repeat.

  • Task store — JSON on disk, derived mechanically from the plan's task table (the hand-retyping step is where yesterday's flight lost its per-item roles). Only the framework writes state: a worker files a typed claim ("I believe this passes; here's the evidence"), and the store flips only when the framework's own verification corroborates it. Claiming is atomic behind an interface (file lock now; swappable if we ever fan out hard). status is a file read.
  • The loop — a script. Mechanical selection, prompts assembled by concatenating durable files scoped to the task, judgment never inside. The boundary, stated exactly: no routine per-cycle decision is ever a model's — models appear only as dispatched workers, judges, and planners whose typed outputs the deterministic loop applies. Triggers dispatch an ephemeral judge that returns a typed decision (split / re-brief / re-bind / park / impossible — never "try again"). A task that fails on ambiguity goes straight to escalation, not retry. A failure that smells like quota or overload burns no attempts and backs off; if it persists, the run parks with a note in your inbox — no reset-time cleverness in v1, and budget integration (agent-spend) is deferred.
  • Dispatch adapters — the only place vendor knowledge lives. The roster (delegate) binds a role to a mind; the adapter wraps that mind's CLI: structured output, sandbox flags, transcript capture, secrets hygiene on retained logs. Adding a future agent CLI costs one adapter. Dropped: building the loop on any vendor's native daemon, goal, or hook machinery — the loop stays ours and vendor-blind; vendor docs contribute research insights, not dependencies.
  • Process lifetime — framework-owned and vendor-neutral: the supervisor writes heartbeat files (liveness is a file read, never ps), owns each worker's process group, and kills by group with the kill path outside anything a worker can write. A drain verb (finish the current task, then stop) is distinct from kill — the babysitter that killed a healthy segment yesterday had no such verb.
  • Verification runner — the firing mechanism behind rules the skills today state only as prose. "Never weaken a test" is currently an instruction; here it's visibility with teeth, not a straitjacket: test and check files are fingerprinted, and any test edit rides the task's evidence as a first-class diff. A task whose brief includes test changes (a refactor, an API rename) proceeds normally; an out-of-scope test edit withholds the flip until a judge has read the diff. Zero ceremony in the honest case, one targeted look in the suspicious one — and workers are never blocked from doing the right thing to a test that no longer compiles. "A self-report is a claim, not evidence" extends to exit codes, which are one-bit self-reports from a process the worker shaped: pytest exits 0 when it collects zero tests, so deleting a test file makes the suite "pass" — the runner reads the result artifact instead (which tests ran, at which commit), and a shrinking test count without a recorded decision is red. And one task's bad paperwork can only redden that task: yesterday one empty command list killed the whole run for two hours because "broken" wasn't distinguished from "red" — verdicts are a closed enum (green / red / infra / killed / malformed) and only malformed machinery stops the line.

needs yesAdoptions from the research

Distilled to what we strongly believe earns a place, one line of evidence each. Strike any row.

AdoptBecause (measured)
Small tasks, fresh context The horizons are measured in human task length: at the ~80% reliability unattended work needs, agents succeed on tasks a skilled human finishes in roughly half an hour, and success drops fast above that. So tasks stay small in work content — never sized in predicted time, which we already forbid and which agents estimate badly anyway. Separately: models err more when their context holds their own earlier errors, at every model scale.
Failure ends the slice Corollary of the above: an agent that just failed a task doesn't pull the next one in the same context; greed applies to success streaks. (Refines your pull premise.)
Checks out of reach Agents were observed forging exit codes, patching evaluators, and editing tests; anti-cheating prompting left a 54% residual. Our mitigation keeps refactors possible: fingerprint tests and checks, surface every edit as evidence, gate only out-of-scope edits on a judge — and judge artifacts, never exit codes.
Ambiguity → escalate Cheating jumps ~20× on under-specified tasks. Retrying an ambiguous task manufactures increasingly creative fakes. (Also: intake was right all along.)
Deterministic stall detection first Stuck-detection uses cheap mechanical signals: nothing changed on disk for N cycles, the same error text repeating, output collapsing, a wall-clock cap. The alternative — a second model on a timer reading the run and judging "is it stuck?" (what your babysit.py did) — is measured to flag late and cost ~11% overhead. So: no periodic poller; the ephemeral judge fires only when a mechanical signal trips.
Task sizing by check Every task owes a fast, objective check; a task that can't have one is judgment-anchored by definition and routes through the bless path. One rule sizes the tasks and sorts the anchors.
Tasks carry decisions Fresh contexts lose tacit decisions; the task record carries interfaces, file paths, and out-of-scope lists — not just a title.
Steal from Bernstein, don't adopt An existing OSS deterministic orchestrator has solved task lifecycle, fail-closed verification, respawn-then-park, and escalation receipts; it's enterprise-heavy, so we take mechanisms, not the dependency.
Prune on model upgrades Every control encodes an assumption about what models can't do; re-test and strip on each model bump so the harness doesn't fossilize.

needs yesWho does what — the UX contract

  • The agent you're chatting with is the entrypoint: runs intake with you, invokes scaffold, and — because it invoked the planner — it owes you the plan as a readable page (HTML/artifact) in your chat, and the link to this kind of review surface. On your yes it also starts the run and says so plainly — "started; you can close this chat" — and tells the truth about the machine: a laptop-local run pauses when the lid closes and resumes safely on wake. A scaffolded thing never silently "gets set up and then… nothing".
  • The planner (blind, fresh context) writes the contract: tasks with checks, anchor choices, the demonstration list, the review severity bar, and the handoff phase naming its owner. When a skill named handoff is available, the planner invokes it up front — so evidence tracking and the proof surface are set up at plan time (handoff's accumulation half), and the handoff phase runs its production half at the end.
  • The framework owns everything between your two acts: the loop, verification, status, escalation delivery, process lifetime.
  • Workers pull, work, file claims, capture demonstrations at first pass. Judges return typed decisions and end.
  • The handoff owner (a planned task like any other) runs production scrutiny and writes the front page — an HTML file in the repo.
  • You appear exactly four times: intake, plan approval, async escalation answers, and the stamp. Close the chat whenever you like; any fresh agent picks up from disk.

needs yesHow it gets built

  • Codex implements against this design once you approve it.
  • The framework has its own goal function — our medicine, self-applied: a toy flight runs end-to-end unattended from a fresh checkout (init → plan → loop → induced stall → escalation → wrap), plus seeded-failure tests for every failure class from yesterday's autopsy and the feedback log.
  • Then the skills are reworded around the shipped framework (scaffold's verification section carries the settled model above; handoff and delegate get the responsibility prose), and one codex review sweeps the whole pipeline against our principles — bounded by a stop bar fixed before dispatch.
